# ProgramBench：Reman / Claude Code / dsh

同一道题、同一个模型，换不同 agent 脚手架，比**做没做出来**、**用时**和**花费**。

选题见 [TASKS.md](TASKS.md)，跑法与记录口径见 [README.md](README.md)。

## 要比什么

| 指标 | 定义 |
|---|---|
| 结果 | `programbench eval` 给出的**通过率**（通过用例 / 总用例，跳过算未通过）与**是否解出**（全部用例通过） |
| 用时 | **agent 自己干活的那一段**：`run.json` 的 `elapsed_seconds`，从题面发出到 agent 收工，不含装脚手架、建成员、判分 |
| 花费 | token 用量乘 DeepSeek 官方价（`eval/pricing.json`：命中 0.02 / 未命中 1 / 输出 4 元每百万），分三段 |
| 压缩次数 | 上下文被压缩几次：按「上下文比上一条少 40% 以上且少 5 万 token」的断崖数，与各家自报的压缩事件互证 |

## 统一设置

| 项 | 值 |
|---|---|
| 模型 | `deepseek-flash`（Claude Code 走 Anthropic 兼容端点 `https://api.deepseek.com/anthropic`） |
| 思考强度 | `high`（三家都显式设置） |
| 输出上限 | **65,536**（三家一致） |
| 压缩触发点 | **≈35 万 token**，三家一致；窗口按各家策略倒推：reman **500,000**（×0.7=350,000）、dsh **480,000**（−65,536−65,536=348,928）、cc **440,000**（×80%=352,000） |
| 题面 | **官方英文 `instruction.md` 原文**，逐字节复制（`prompts/<题>.md`），不加任何中文说明、不加任何额外提示 |
| 资源 | 每个 agent 容器 **4 CPU / 8 GB**（题目本身不带资源推荐值，这是统一设定） |
| 网络 | agent 期在 `--internal` 内网里，唯一能连的是白名单代理（只放行 `api.deepseek.com`），对应题面「没有互联网」 |
| 审批 | 都不打断：cc `--dangerously-skip-permissions`；dsh `--permission-mode danger-full-access`；reman 工具全 `allow` |
| 并发 | **3**：三家同时跑，各自一个容器 |
| 每道题 | 每个 agent 跑 **1 次** |
| 时长上限 | 第一道 `jplot` 为单场 3 小时；**从第二道 `go-critic` 起统一改成 2 小时**（`run.py --timeout` 默认 7200）。九场都没有一家跑到上限 |
| 判分 | `programbench eval` 逐场判；`jplot` 与 `typst` 判分开过宿主代理 `PROGRAMBENCH_CONTAINER_PROXY`（pypi / 依赖），`go-critic` 没用到外网 |

## 局限

- **九场里每题每家只跑一次**，没有分布（复测另算：`typst` 多跑 1 次、`go-critic` 多跑 3 次）。同一家在不同题上差距很大（reman 从 92.94% 掉到 39.36%），单次结果分不清是能力差异还是这一场的运气。
- **并发 3**：三家同时跑，机器 16 核、每家 4 核；`typst` 判分还与 dsh 那一场同时在跑。单独跑可能更快，这里没测。

## 观察

- **`jplot` 和 `typst` 上三家差别很小**：`jplot` 极差 7.75 个百分点（87.26%–95.01%），`typst` 极差 2.07 个百分点（50.90%–52.97%）。这个量级落在模型自身的随机性范围内，不足以说明谁的脚手架更好。
- **`go-critic` 上 reman 的那一场**：43 分钟收工，通过率 **39.36%**，比 cc（64.41%）和 dsh（65.41%）低约 25 个百分点。这道题后来又多跑了三次，通过率从 22.84% 到 68.40%，单场差别不足以说明脚手架好坏，四次数字见下面的复测节。

## 结论

模型只有一个，而且 `deepseek-flash` 本身不稳定：单题的结果没有可比性，只有把题量加到一起看才有意义。**但样本只有三道题、每家一次，下面这个判断只能算非常粗浅的印象，不能当结论用。**

三题合计（见上面的汇总表），**reman 的用时 106 分 30 秒、花费 ¥6.20，都是三家最低**（cc 250 分 31 秒 / ¥15.61，dsh 156 分 56 秒 / ¥13.40）；通过率上看不出高下。

把复测里 reman 任一单题的数字换进合计（`go-critic` 38 分 33 秒 / ¥2.31、`typst` 46 分 26 秒 / ¥3.57），合计仍是三家最低，结论不变。

## 复测：reman / `typst`（新版运行时，一次）

**两个词先说清楚**

- **旧版 / 新版运行时**：旧版是 11-14 及以前那版；新版是 11-15 对提示词与文案做了一轮整理之后的版本。
- **旧版 / 新版通道**：旧版通道是 reman 脚手架建一个真人成员、以成员身份私聊发题面；新版通道是以用户身份
  直接对话发题面。

**口径**：与九场相同（见上面「统一设置」），单场只跑 reman 一家。

**结果**

| 次序 | 运行时 | 通道 | 通过率 | 通过 / 失败 / 跳过 | 用时 | 未命中 / 命中 / 输出 | 命中率 | 花费 | 压缩 | 撞时限 |
|---|---|---|---|---|---|---|---|---|---|---|
| 第一次（1114-2305） | 旧版 | 旧版 | 50.90% | 909 / 876 / 1 | 25 分 22 秒 | 125,291 / 50.06M / 245,484 | 99.75% | ¥2.11 | 0 | 否 |
| 第二次（1115-0721） | 新版 | 新版 | **53.64%** | 958 / 827 / 1 | 46 分 26 秒 | 485,926 / 81.94M / 362,224 | 99.41% | ¥3.57 | 1 | 否 |

两次之间运行时与通道一起换了，所以上面两行的差别不能归给其中任何一个。

第一次判分跑出 0 分是判分链故障（宿主代理转发进程不在，10 个分支全部 `results_read_failed`），重判后为上表
的 53.64%；0 分那次不计入任何对照，经过见 [README.md](README.md) 的失误汇总。

## 复测：reman / `go-critic`（新版运行时，单变量）

第一次在这道题上是 39.36%，与另外两家（cc 64.41%、dsh 65.41%）差得多，所以接着补跑了三次，四次都列在下面。
第三次之前换了题面投递通道（前两次是 reman 脚手架建一个真人成员、以成员身份私聊发题面，之后改成以用户身份
直接对话发题面）；第四次与第三次只差运行时版本，其余口径不变，所以这一组是单变量对照。运行时与通道的定义见上一节。

**但这不能证明分数变化是通道或运行时造成的**：`deepseek-flash` 不稳定的判断在做 Terminal-Bench 那批时就已经得出
（同一题、同一套设置下结果能差很多），单场差别不足以归因。
